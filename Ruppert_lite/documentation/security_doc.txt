║          🔒 SECURITY ARCHITECTURE 🔒                          ║
╚════════════════════════════════════════════════════════════════╝

Techpack is designed as a resilient local mesh of devices operating in a compact wearable or backpack environment. Security must protect network trust, command execution, file sync, and device identity without forcing heavy infrastructure or centralized authority. The design must remain suitable for low-power devices, temporary devices, and mixed device classes.

┌─────────────────────────────────────────────────────────────┐
│  🎯 SECURITY GOALS                                              │
└─────────────────────────────────────────────────────────────┘

The security model must satisfy the following:

- Protect device identity against spoofing or impersonation
- Prevent unauthorized command execution across the mesh
- Restrict device administration to trusted authority layers
- Allow manual onboarding for new devices without hard-coded universal trust
- Ensure command replay and credential reuse are detectable
- Preserve local operation when a device loses network connectivity
- Keep implementation lightweight enough for Arch-based x86 and ARM devices

┌─────────────────────────────────────────────────────────────┐
│  ⚙️  CORE PRINCIPLES                                            │
└─────────────────────────────────────────────────────────────┘

The security model is intentionally layered and follows these rules:

- PackService: No authority- collects information, emits packets, must request permissions. These are the project tools.
- TechNet is responsible for packet creation, transport, and network discovery. The way the tools communicate.
    - MsgBus is a transport envelope only. It exposes only the headers required to route a packet.
- TechNetAdmin is the only authority layer for identity, permissions, verification, and admin actions. Permission for tools to operate.
    - Authorization is separated from payload content.
    - Device permissions are restricted

┌─────────────────────────────────────────────────────────────┐
│  👤 IDENTITY MODEL                                              │
└─────────────────────────────────────────────────────────────┘

Each device must carry a stable device identity, distinct from user-facing aliases.

- A device has a persistent self ID generated during registration or first secure onboarding
- Device aliases are user-facing labels and may change in config
- Device identity is for trust and accountability, not display
- A device may also carry a temporary first-contact or mutual-trust identity for local mesh recognition
- Temporary/unknown devices are generated an ID + an ID signifying low trust
-Devices will create a "fistbump" ID on first contact, meaning each device will have unique ID's for each other device to prevent device impersonation
    -On detection, packets from potentially corrupt device will be stored in logs on a segregated drive partition and Rupert+user will be notified

This supports both durable identity and temporary peer trust without conflating the two concepts.

┌─────────────────────────────────────────────────────────────┐
│  🤝 FIRST-CONTACT ONBOARDING                                    │
└─────────────────────────────────────────────────────────────┘

First contact between two devices cannot be assumed safe by default. A network participant must prove identity before it is trusted.

Techpack supports multiple bootstrap methods depending on the device type:

- High-capability devices: factory-provisioned credentials or administrator-assisted onboarding
- Low-capability devices: manual pairing, QR-based verification, or a secure local setup flow
- Temporary guest devices: limited access only until explicit trust is granted

A device must not automatically trust another device simply because it is present on the same subnet or mesh.

┌─────────────────────────────────────────────────────────────┐
│  🤜🤛 MUTUAL TRUST & FISTBUMP IDENTITY                          │
└─────────────────────────────────────────────────────────────┘

After a secure first contact, two devices may establish a mutual fistbump ID. This is a peer-specific trust record that is stored locally on both devices.

The fistbump ID exists to support:

- device-to-device trust recognition
- replay detection
- impersonation detection
- local verification without a central registry

This identity is not the same as a universal device ID and should not be treated as a global authority marker.

┌─────────────────────────────────────────────────────────────┐
│  📋 AUTHORIZATION MODEL                                         │
└─────────────────────────────────────────────────────────────┘

Authorization is intentionally separated from payload transit.

A packet contains three layers:

- MsgBus: routing only
- Authorization: identity, trust, permission, and proof
- Payload: command, telemetry, or state information

This means a packet cannot be trusted just because it reached the right device. The receiving device must validate authorization before acting on the payload.

┌─────────────────────────────────────────────────────────────┐
│  🏆 PERMISSION TIERS                                            │
└─────────────────────────────────────────────────────────────┘

Permission levels should be defined in the authorization layer and enforced at command execution time.

Suggested initial structure:

- Tier 1: administrative actions
  - command execution
  - updates
  - device reconfiguration
  - permission changes
- Tier 2: logging and local state access
  - log reads
  - retention or sync actions
  - telemetry export
- Tier 3: network-level actions
  - discovery
  - heartbeat
  - mesh presence
  - route propagation

These tiers should be refined later, but the key rule is that higher-impact actions require stronger proof with lower network access being accessable without network permissions.

┌─────────────────────────────────────────────────────────────┐
│  👑 ADMIN AUTHORITY                                             │
└─────────────────────────────────────────────────────────────┘

A device may only act with authority when it can prove it is authorized by the local admin model.

The admin authority layer must support:

- manual user proof for administrative actions, intially performed by external trusted device
- device-level permission checks
- temporary or delegated action approval
- secure rejoin or recovery of a lost device
- protection against stolen or replayed admin commands

The admin proof should be scoped to specific actions and should not be treated as a permanent universal grant.

┌─────────────────────────────────────────────────────────────┐
│  🎫 SESSION TOKEN MODEL                                         │
└─────────────────────────────────────────────────────────────┘

Session tokens are required for transient trust windows, especially where commands are issued across the mesh.

Session tokens should include:

- device identity
- session scope
- expiration window (shorter means more commands processing)
- usage restrictions
- proof of issuance by an authorized layer

Tokens should not be accepted permanently. They should be short-lived and audited.

┌─────────────────────────────────────────────────────────────┐
│  ⏰ TIME-BASED COORDINATION                                      │
└─────────────────────────────────────────────────────────────┘

The ecosystem may optionally use a shared internal network calendar to mantain a consistent internal ecosystem and operate as another sign of devices intruding on network

This feature is useful only if:

- clocks are reasonably synchronized (perhaps only kept up to the day, maybe hour)
- skew tolerances are defined
- replay windows are bounded
- fallback behavior is specified for drift

This should be treated as an optional security enhancement, not the foundation of the entire trust model.

┌─────────────────────────────────────────────────────────────┐
│  🔐 ENCRYPTION & KEY HANDLING                                   │
└─────────────────────────────────────────────────────────────┘

Private keys and sensitive trust data must be stored in encrypted local storage. At minimum:

- private keys must never be stored in plaintext
- device registration data must be protected
- authorization material must be isolated from payload logs
- admin proof material must not be exposed in ordinary telemetry

Encryption strategy should be lightweight and local-first, with the emphasis on device-local security rather than heavy central key infrastructure.

┌─────────────────────────────────────────────────────────────┐
│  🔄 RECOVERY & LOCKOUT                                          │
└─────────────────────────────────────────────────────────────┘

The system must define recovery behavior for:

- lost or stolen devices
- device re-registration
- compromised peer devices
- offline device rejoin
- admin lockout scenarios

A recovery path should exist without requiring a universal network key. Recovery must be explicit, auditable, and permission-scoped.

┌─────────────────────────────────────────────────────────────┐
│  📊 SECURITY LOGGING & AUDIT                                    │
└─────────────────────────────────────────────────────────────┘

Security events should be logged at the authorization layer:

- new device trust establishment
- failed permission checks
- replay/reuse detection
- token expiration
- admin command attempts
- device recovery and lockout actions

Security logs should be separate from ordinary telemetry and should not be used as a general-purpose data store.

│  ❓ OPEN DESIGN QUESTIONS                                        │

The following items must be decided before auth implementation begins:

- What is the exact first-contact bootstrap flow?
    1) TechOS install from drive/external device
    2) First time user set up (new technet) OR option to connect to local TechNet using password created by user on intial setup. This process is a manual add.
    3) On successful connecct, additional devices are added through further additional adds while less intelligent devices  will connect to host device where the add key must then be entered.
- Should auth be based on signed tokens, challenge-response, or a hybrid?
    
    Intial authority will be granted with a challenge response, on passing the device will be assigned an authoirty token with an expiration of 1 hour

- What is the trust lifetime for fistbump IDs?

    For now, all trust will survive for one hour before requiring a refresh

- What is the admin proof derivation model?

    The hardest design question for security on this system.

- How is permission enforcement placed: centralized or distributed?

    Must be distrubuted 

- What is the recovery flow for a locked-out device?

    Reset of device + reconnection to network followed by a fresh update of local data from network
- What is the acceptable clock skew for any time-based security mechanism?

    1 hour until I have a good reason to suspect it isn't

┌─────────────────────────────────────────────────────────────┐
│  📍 SECURITY SCOPE FOR THIS PROJECT PHASE                       │
└─────────────────────────────────────────────────────────────┘

For the current project phase, the following should be treated as required:

- device identity
- peer trust establishment
- authorization separation from payload
- layered permission model
- admin proof flow
- replay protection
- encrypted local key material

The following should be deferred until the trust model is finalized:

- dynamic trust graph expansion
- full policy engine
- advanced revocation propagation
- highly complex time-based key sequences
- deep service-to-service federation
